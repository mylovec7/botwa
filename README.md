# CHELYN

Ultra-light WhatsApp worker with exactly one job: stay connected and
automatically mark visible WhatsApp Status updates as viewed. Nothing else.

## What it does

- Connects to WhatsApp using [`@whiskeysockets/baileys`](https://github.com/WhiskeySockets/Baileys)
  with a **pairing code** (no QR).
- Persists the session locally so restarts don't require re-pairing.
- Auto-reconnects on network drops with simple backoff.
- Marks any visible Status update as viewed the moment it's detected —
  no reply, no reaction, no download, no forwarding, no duplicate processing.
- Exits non-zero on a fatal error so a process supervisor (e.g. Hostless)
  restarts it.

It has no database, no HTTP server, no AI, no command handling, no
scheduler, and no web panel. If you need any of that, this is the wrong
project to extend — build a separate one.

## Setup

```bash
npm install
cp .env.example .env
# edit .env and set WHATSAPP_PHONE_NUMBER
npm start
```

On first run (no saved session), CHELYN prints:

```
Pairing required
Enter this pairing code on your phone: XXXX-XXXX
```

Enter that code on your phone under **WhatsApp → Linked Devices → Link with
phone number**. The code is generated by WhatsApp itself through Baileys —
it is never invented or hardcoded, and it's only ever printed to the
console once, never written to disk or logged again.

Once linked, the session is saved under `session/` (or whatever
`AUTH_DIR` points to). Subsequent restarts reconnect silently as long as
that folder is intact and WhatsApp hasn't invalidated the session.

## Environment variables

| Variable | Required | Description |
|---|---|---|
| `WHATSAPP_PHONE_NUMBER` | yes | Country code + number, digits only (e.g. `15551234567`) |
| `AUTH_DIR` | no | Where session state is persisted (default: `session`) |

Never commit `.env` or the `session/` folder — both are already in
`.gitignore`.

## Why Baileys 6.7.23 (not the 7.0.0 line)

As of this writing, `@whiskeysockets/baileys` has an actively developing
`7.0.0-rc` line with breaking API changes and a higher Node.js requirement,
and multiple open reports of connections silently dropping shortly after
pairing on recent `rc` builds. `6.7.23` is the last release on the older,
widely-deployed API and is the version this codebase's pairing-code,
session-persistence, and `readMessages` calls are written against. If you
want to try the 7.0.0 line once it stabilizes, check the library's own
migration guide first — the event/API shapes changed (e.g. `sock.ev.process()`,
a required `getMessage` callback) and this code was **not** written or
tested against that line.

## Deploying to Hostless

This targets a **Background Worker** style deployment (long-running
process, no public HTTP port needed):

1. Push this repository to GitHub (session/credentials are excluded via
   `.gitignore` — verify they weren't force-added before pushing).
2. In Hostless, create a Background Worker service pointed at this repo.
3. Set the start command to `npm start`.
4. Set `WHATSAPP_PHONE_NUMBER` (and `AUTH_DIR` if you're not using the
   default) as environment variables in Hostless's dashboard.
5. Point `AUTH_DIR` at Hostless's persistent storage/volume mechanism so
   the session survives restarts and redeploys — **not** the ephemeral
   filesystem, if Hostless distinguishes between the two.
6. Enable automatic restart / restart-on-failure if Hostless exposes that
   as an option, so a fatal-error exit gets picked back up.

**I have not verified Hostless's exact menu names, the specifics of its
persistent-storage mechanism, or its restart-policy setting** — "Hostless"
isn't a platform I have reliable, current documentation for, and I don't
have network access to look it up right now. Please confirm those three
items (persistent volume setup, background worker type, restart-on-failure
toggle) against Hostless's own current docs before treating this as
production-ready. Nothing else in this project depends on
Hostless-specific behavior.

## Testing

I could not run this end-to-end myself — pairing against a real WhatsApp
account and exercising reconnect/crash behavior needs live network access
and a real phone, which this environment doesn't have. The code is written
directly against Baileys' documented API (verified via its current README
and migration docs), but please run through these manually before trusting
it in production:

1. **First login** — no `session/` folder, run `npm start`, confirm a
   pairing code appears, link it, confirm `session/` gets created.
2. **Normal restart** — stop and restart the process, confirm it
   reconnects without asking to re-pair.
3. **Network disconnect** — disconnect your network briefly, confirm it
   logs `Disconnected` / `Reconnecting` and comes back without spawning
   extra processes.
4. **Process crash** — kill it (`kill -9`) under your supervisor, confirm
   the supervisor restarts it and it reconnects using the saved session.
5. **Redeploy** — redeploy on Hostless, confirm the session persists and
   no re-pairing is requested.
6. **Status auto-view** — post/view a Status from another account,
   confirm it's marked viewed exactly once, with no reply/reaction/download.
7. **Idle resource use** — with nothing happening, confirm CPU stays near
   zero (no polling loop — everything here is event-driven).
